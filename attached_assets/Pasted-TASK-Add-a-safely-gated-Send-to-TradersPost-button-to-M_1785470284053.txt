TASK: Add a safely gated Send to TradersPost button to Main Brain.

GOAL

Allow the operator to manually send the current canonical READY trade plan to the existing TradersPost integration from Main Brain.

This is not a new execution pathway.

Reuse the existing TradersPost endpoint, payload builder, authentication, duplicate guard, risk guard, and execution logging.

CRITICAL SAFETY REQUIREMENT

The button must never bypass any existing execution gate.

It must not send:

- WAIT setups
- POTENTIAL setups
- NOT ACTIONABLE setups
- blocked setups
- stale plans
- invalid stops
- missing risk plans
- plans that conflict with active-trade restrictions
- plans blocked by daily loss or prop rules

STRICT SCOPE

DO NOT modify:

- strategy selection
- Edge Score
- readiness
- risk thresholds
- position sizing
- entry/stop/target calculations
- opposing-structure rules
- learning
- Databento
- TradersPost payload semantics
- broker credentials
- duplicate-trade rules
- active-trade logic

PART 1 — TRACE THE EXISTING SEND PATH

Locate the current production path that sends a trade to TradersPost.

Document:

- frontend trigger, if one exists
- backend endpoint
- canonical payload builder
- authentication
- readiness validation
- risk validation
- duplicate guard
- active-position guard
- broker-ready guard
- audit logging
- success response
- rejection response
- retry behavior

Do not create a second webhook implementation.

PART 2 — BUTTON PLACEMENT

Place the button inside the Main Brain TRADE PLAN panel.

Label when enabled:

SEND TO TRADERSPOST

Do not place it in the page header because the action must stay visually tied to the exact trade plan being sent.

PART 3 — BUTTON ELIGIBILITY

Enable only when all existing canonical requirements pass.

At minimum, verify:

- candidate status is READY
- verdict is actionable
- trade plan is valid
- instrument is supported
- direction is present
- entry is present
- stop is present and valid
- target is present
- risk sizing is valid
- TradersPost is configured
- broker is ready
- database is ready
- no hard alert block
- no execution lock
- no duplicate signal
- no conflicting active-trade restriction
- plan is fresh

The backend must revalidate all requirements.

Frontend disablement alone is not sufficient.

PART 4 — DISABLED STATES

When disabled, show the exact reason.

Examples:

WAITING FOR BULLISH BOS
TRADE NOT ACTIONABLE
RISK STATE BLOCKED
TRADERSPOST UNAVAILABLE
STOP INVALID
PLAN STALE
DUPLICATE SIGNAL
ACTIVE TRADE CONFLICT

Do not show a clickable enabled button when a required field is missing.

PART 5 — CONFIRMATION STEP

Before sending, require a confirmation dialog showing:

- instrument
- direction
- strategy
- mode
- entry
- stop
- targets
- contracts
- dollar risk
- risk/reward
- current readiness
- data age

Confirmation action:

CONFIRM AND SEND

Cancel action:

CANCEL

Do not allow accidental one-click transmission.

PART 6 — IDEMPOTENCY

Generate or reuse a stable signal/trade-plan identifier.

Repeated clicks or network retries must not create duplicate orders.

The backend must reject a duplicate safely and return an explicit response.

PART 7 — SUCCESS AND FAILURE STATES

Success:

SENT TO TRADERSPOST
Include timestamp and existing request/trade identifier.

Rejected:

NOT SENT
Show the exact backend rejection reason.

Unknown network result:

STATUS UNKNOWN — VERIFY BEFORE RETRYING

Do not automatically retry an uncertain execution request.

- duplicate result

- final status
