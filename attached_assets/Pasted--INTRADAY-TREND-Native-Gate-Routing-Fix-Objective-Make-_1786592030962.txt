# INTRADAY_TREND — Native Gate Routing Fix

## Objective

Make **one narrow architectural correction**:

`INTRADAY_TREND` must use its **native intraday setup/confirmation/risk pipeline for READY/WAIT**, rather than first requiring the inherited SWING strict gate.

This is **not a strategy redesign**.

Do not add indicators, strategies, thresholds, scoring systems, or unrelated cleanup.

---

## 1. Preserve SCALP and SWING Exactly

Do not change the behavior of:

* `SCALP`
* `SWING`
* ORB
* execution
* order routing
* prop/risk protections
* global safety controls

Run regression tests before and after and prove SCALP/SWING decision behavior is unchanged.

---

## 2. Remove the SWING Prerequisite From INTRADAY_TREND Only

Current architecture effectively behaves as:

`INTRADAY_TREND`
→ inherited `evaluate_strict_setup`
→ SWING strict gates
→ IT native gates
→ READY

Because:

`MODES["INTRADAY_TREND"] = dict(MODES["SWING"])`

IT currently inherits the SWING `EDGE_READY_THRESHOLD = 85`.

It also must satisfy the legacy strict requirements:

* `zone_valid`
* `vwap_confirmed`
* `structure_confirmed`
* `edge_score >= 85`

before the native IT gate gets a chance to approve the trade.

Change **only INTRADAY_TREND routing** so these legacy SWING conditions are no longer prerequisites for IT READY.

Do not delete these calculations.

Continue calculating and displaying them for diagnostics/measurement.

---

## 3. IT Must Use Its Existing Native Pipeline

The authoritative IT decision path should become:

`compute_intraday_trend_context()`

→ valid IT context

→ recognized IT setup family

→ IT confirmation sequence

→ `build_intraday_trade_plan()`

→ `_it_entry_veto_reasons()`

→ existing global execution/risk/safety checks

→ `READY` or `WAIT`

Do not create another setup engine.

Use the IT functions already implemented.

---

## 4. Preserve All Existing IT-Native Hard Gates

Do **not** loosen these in this change.

Preserve existing behavior for:

* MNQ-only restriction
* missing/unavailable IT context
* data freshness
* entry/session time restrictions
* force-flat rules
* cooldown
* EXTREME extension/chase protection
* opposed 1H protection
* MID_RANGE location veto
* recognized setup-family requirement
* confirmation sequence
* valid structural stop
* stop must be on correct side
* minimum stop distance of `0.3 × ATR`
* maximum stop distance of `3.0 × ATR`
* maximum chase distance
* minimum intraday R:R
* daily trade cap
* database fail-closed behavior
* execution safety
* duplicate protection
* prop/risk protections
* emergency/safety controls

We are **not loosening the native intraday system**.

We are only removing the requirement that an intraday trade must first qualify as a SWING-style trade.

---

## 5. Keep Legacy Edge Score as Diagnostic Only for IT

Continue computing:

`edge_score`

Continue displaying:

* score
* grade
* contributing signals
* legacy gate result

But for `INTRADAY_TREND`:

`edge_score < 85`

must **not by itself force WAIT**.

Do not change the 85 threshold for SWING.

Do not globally change `EDGE_READY_THRESHOLD`.

Mode-scope this behavior strictly to `INTRADAY_TREND`.

---

## 6. Keep `_it_setup_score` Diagnostic for Now

Do not replace the SWING 85 threshold with another arbitrary IT threshold.

The existing:

`_it_setup_score`

should remain visible/recorded but should **not become a new hard READY threshold in this change**.

We will determine useful IT score thresholds from ghost/live observations later.

## 7. Legacy Zone/VWAP/Structure Should Remain Observable

For IT only, legacy:

* `zone_valid`
* `vwap_confirmed`
* `structure_confirmed`

must no longer independently block READY merely because the SWING strict gate requires them.

However, do **not remove the underlying VWAP, structure, location, BOS/CHOCH, zone, volume or CVD information** from the system.

If the native IT setup/confirmation logic legitimately uses any of those inputs, preserve that native behavior.

The distinction is:

**Remove the inherited SWING veto. Do not remove IT-native evidence.**
