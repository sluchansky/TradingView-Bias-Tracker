TASK: Databento Source Attribution and Double-Counting Audit

CRITICAL CONTEXT

Databento has already replaced most TradingView-derived live market data.

Databento currently writes directly into the shared state used by the existing
Edge Score components, including:

- Current price
- Volume
- CVD / volume delta
- Volatility
- BOS / CHOCH
- HH / HL / LH / LL
- Liquidity sweeps
- Confirmation events

Databento therefore already influences the base Edge Score.

There is currently no separate production
_resolve_databento_score_influence() function and no separate
databento_delta pathway.

DO NOT ADD A DATABENTO SCORE DELTA IN THIS TASK.

DO NOT CHANGE THE DATABENTO INGESTION PIPELINE.

DO NOT CHANGE EDGE SCORES, VERDICTS OR AUTO-TRADE ELIGIBILITY.

OBJECTIVE

Add read-only source attribution and diagnostics so the system can distinguish
which scoring evidence came from Databento and which evidence came from
TradingView.

This task must reveal possible double-counting before any separate Databento
score influence is designed.

PART 1 — PRESERVE THE CURRENT PIPELINE

Do not modify:

- Databento connection or authentication
- Databento subscriptions
- Message handlers
- Symbol mapping
- Reconnect behavior
- Background workers or threads
- Cache structures
- Price calculations
- Volume calculations
- CVD calculations
- Volatility calculations
- Structure detection
- Sweep detection
- VWAP calculations
- Webhook acknowledgment
- Webhook queue behavior
- Existing scoring weights
- Learning influence
- Gate thresholds
- Conflict resolution
- READY / WAIT verdicts
- Auto-trade logic

Databento must remain the primary live market-data source.

PART 2 — IDENTIFY CURRENT SCORE INPUTS

Trace every component used by evaluate_strict_setup() and _edge_for(direction).

For each component, document:

1. Component name
2. Maximum point value
3. State store or input field
4. Function that writes the input
5. Possible sources:
   - Databento
   - TradingView
   - Internal calculation
   - Clock/session logic
6. Which source currently has precedence
7. Whether the gate can distinguish the source today
8. Whether the same market evidence is represented in another component

At minimum inspect:

- BOS
- CHOCH
- Sweep
- VWAP
- Volume
- CVD
- Session
- Volatility modifiers
- Price-based comparisons
- Confirmation alerts

PART 3 — ADD SOURCE METADATA

Where safe and minimally invasive, attach source metadata to new state writes.

Use source labels such as:

source = "databento"
source = "tradingview"
source = "internal"
source = "unknown"

Do not replace existing values or change their shapes if that risks production
behavior.

Prefer a parallel diagnostics structure such as:

MARKET_INPUT_SOURCE_BY_TICKER = {
    "MNQ": {
        "price": {
            "source": "databento",
            "updated_at": "...",
        },
        "volume": {
            "source": "databento",
            "updated_at": "...",
        },
        "cvd": {
            "source": "databento",
            "updated_at": "...",
        },
        "volatility": {
            "source": "databento",
            "updated_at": "...",
        },
    }
}

For alert-driven evidence, preserve source per event:

{
    "alert_type": "BOS",
    "direction": "Long",
    "source": "databento",
    "timestamp": "..."
}

Do not overwrite or remove existing event fields.

PART 4 — SOURCE PRECEDENCE DIAGNOSTICS

Add diagnostics showing, for each directional score calculation:

{
    "component": "BOS",
    "points": 20,
    "source": "databento",
    "source_timestamp": "...",
    "age_seconds": 1.2
}

Produce equivalent entries for all seven score components.

Do not change the score based on source.

The diagnostics must reveal whether a component was populated by:

- Databento
- TradingView
- Internal calculation
- Mixed sources
- Unknown source

PART 5 — DETECT POTENTIAL DOUBLE COUNTING

Add a diagnostics-only audit that flags related evidence appearing in multiple
score components.

Examples:

- Databento aggressor flow represented in CVD and again in confirmation
- The same structure event represented as BOS and confirmation
- The same volume burst represented in Volume and Sweep
- TradingView and Databento copies of the same BOS event both present in
  ALERT_HISTORY
- Databento CVD evidence later reused in a proposed order-flow delta

Return warnings only.

Do not suppress alerts or change points.

Example:

{
    "possible_duplicate": true,
    "evidence_group": "buying_pressure",
    "components": ["CVD", "Volume", "Confirmation"],
    "sources": ["databento"],
    "score_impact": 35,
    "action": "diagnostic_only"
}

PART 6 — TRADINGVIEW AND DATABENTO EVENT DEDUPLICATION AUDIT

Inspect whether TradingView and Databento can publish equivalent events into
ALERT_HISTORY.

Check at minimum:

- BOS
- CHOCH
- Sweep
- Structure confirmation
- Direction
- Instrument
- Time proximity

Add a read-only diagnostic that identifies probable duplicate events using:

- Same instrument
- Same event type
- Same direction
- Within an explicit time window
- Different source values

Do not remove or merge events in this task.

Report how often duplicate candidates appear in tests or fixtures.

PART 7 — NO SEPARATE DATABENTO DELTA

Do not create:

- _resolve_databento_score_influence()
- databento_delta
- Databento score mode
- Databento score cap
- Additional order-flow points
- New score weights
- New hard gates

The existing Databento-fed components remain the only production scoring
influence from Databento.

The Learning Engine remains the only post-base external adjustment.

Current scoring must remain:

base_score = existing component sum

final_score = clamp(
    base_score + existing_learning_delta,
    0,
    110
)

Do not change this formula.

STOP CONDITIONS

Stop and report before modifying code if:

- Adding source metadata requires changing the Databento data structures used
  by production scoring
- Existing tests fail before changes
- Databento source precedence is unclear
- TradingView currently overwrites newer Databento values
- Duplicate events are already being counted twice in production scoring
- HEAD changes unexpectedly

If any stop condition is found, do not repair it during this task.

Report the finding and wait for approval.
