OBJECTIVE

2. DATABASE VALIDATION

3. SNAPSHOT CAPTURE VALIDATION

Prove that a snapshot is created only when:

- A setup reaches READY, or
- An auto-trade candidate reaches the intended capture point

Test at minimum:

- READY setup captured once
- Repeated READY evaluation not duplicated
- WAIT setup not captured
- Opposite direction treated as a separate setup
- Different instrument treated separately
- New setup after prior trade closure can be captured

4. _DQ_PENDING_BY_INST LIFECYCLE

Audit every path that adds, reads, and removes entries from `_DQ_PENDING_BY_INST`.

Confirm it is cleared after:

- Winning trade closure
- Losing trade closure
- Breakeven closure
- Manual closure
- Trade cancellation
- Setup invalidation, if applicable
- Failed snapshot insertion
- Failed outcome update
- Application restart

If restart persistence is intentionally handled by database lookup rather than memory, document that behavior.

Do not repair unrelated lifecycle behavior during this validation. Stop and report if a stale-key risk exists.

5. OUTCOME MATCHING

Prove that a closed trade updates the correct snapshot using:

- Instrument
- Direction
- Strategy or mode
- Setup identity or snapshot ID
- Trade identity where available

Verify that an old unresolved snapshot cannot accidentally receive the outcome of a newer trade.

Test:

- Sequential trades on the same instrument
- Long followed by Short
- Scalp and Swing on the same instrument
- Two instruments closing near the same time
- Duplicate closure notification
- Closure with no matching snapshot
