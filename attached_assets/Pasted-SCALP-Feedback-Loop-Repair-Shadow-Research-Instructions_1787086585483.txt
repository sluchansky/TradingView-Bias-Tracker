SCALP Feedback Loop Repair & Shadow Research Instructions

Objective

Repair and validate the SCALP research/feedback pipeline so we can accurately compare:

SCALP evaluation → gate decision → READY/blocked → hypothetical or actual outcome → gate effectiveness

This phase is instrumentation and research only.

DO NOT change live trading behavior, thresholds, gate hardness, risk sizing, execution logic, or strategy selection.

The goal is to make the data trustworthy before optimizing the SCALP strategy.

⸻

Audit:

1. gate_audit_log
2. ghost_observations
3. READY outcome/backfill watcher
4. SCALP research/paper-sim tables
5. SCALP strategy/setup identification
6. Gate-effectiveness recorder

* Counts by instrument
* Counts by direction
* Counts by strategy/setup
* Number of READY observations

Specifically explain why:

* trend_alignment is missing from almost all audit records.

Do not assume the cause. Trace the actual code path.

PHASE 2 — Repair READY Outcome Resolution

Audit the watcher responsible for closing observations.

Determine why blocked counterfactual observations resolve but READY observations remain PENDING.

A valid READY observation must eventually transition from:

PENDING

to an appropriate terminal state such as:

TP1
TP2
STOP
BE
EXPIRED
INVALIDATED
DATA_UNAVAILABLE

Use the project’s existing outcome definitions wherever they already exist.

Do not introduce competing definitions of TP/STOP outcomes.

The resolver must survive:

* application restart
* republish
* worker restart
* temporary Databento interruption
* missing bars
* delayed bars
* duplicate watcher cycles

Processing must be idempotent.

The same observation must never be closed twice.

⸻

PHASE 3 — Fix Bar/Watcher Data Access

Explicitly verify that the watcher can access the actual live/historical bar source used by the application.

This project has previously experienced worker failures caused by modules looking for bar data in the wrong module/global scope.

Verify the dependency path rather than assuming it works.

Add a regression test proving:

1. Observation is created.
2. Bars become available.
3. Watcher sees those bars.
4. TP or stop is detected.
5. Observation transitions out of PENDING.
6. Restarting/rerunning the watcher does not duplicate the result.
