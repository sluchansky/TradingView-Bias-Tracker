# STEP 3 — DEFINE THE CANONICAL GHOST OBSERVATION

Every valid strategy setup must be capable of creating one canonical research observation.

The observation must represent:

**WHAT THE STRATEGY ACTUALLY KNEW AND INTENDED AT SIGNAL TIME.**

At minimum, preserve:

* observation ID
* strategy ID
* strategy version if available
* configuration version if available
* instrument
* direction
* signal timestamp
* intended entry
* intended stop
* intended targets
* R risk distance
* source mode
* session/time context
* relevant strategy context snapshot
* lifecycle status
* final outcome
* MFE
* MAE
* gross R
* estimated cost R
* net R
* close timestamp

Reuse existing fields/models whenever possible.

Do NOT create a second competing trade-history system.

---

# STEP 4 — IMMUTABILITY IS REQUIRED

Once the ghost observation is created, the trade plan must be frozen.

The following must NOT change because a strategy/configuration changes later:

* original entry
* original stop
* original targets
* original strategy
* original direction
* original signal time
* original relevant context
* original strategy/config version

If existing models are mutable, add the minimum snapshot mechanism required.

Historical research results must reflect the rules that existed when the setup occurred.

---

# STEP 5 — GHOST OBSERVATIONS MUST BE INDEPENDENT OF LIVE EXECUTION

This is critical.

A valid research setup must still be observable even when a real order is blocked by:

* live execution disabled
* arm state
* safety lock
* emergency stop
* prop rule
* daily loss limit
* max position limit
* correlated exposure limit
* duplicate execution guard
* account unavailable
* broker failure

The research question is:

**What would this strategy have done?**

That is separate from:

**Was the account allowed to execute it?**

Do not bypass safety controls for real orders.

Instead, ensure the ghost/research path happens before or independently of live execution permission where architecturally appropriate.

---

# STEP 6 — DO NOT CREATE FAKE SIGNALS

Ghost trading must only begin when the existing strategy engine produces a legitimate setup under its current rules.

Do NOT:

* loosen thresholds
* create extra signals for sample size
* fabricate theoretical setups
* replay future information into current signals
* change strategy qualification logic

The research pipeline observes current strategy behavior exactly as-is.

---

# STEP 7 — DEFINE ENTRY ACTIVATION CORRECTLY

A ghost observation should distinguish:

**SETUP CREATED**

from

**ENTRY ACTUALLY TRIGGERED**

where relevant.

If a strategy requires price to touch/cross/retest an entry before becoming active, preserve that behavior.

Do not automatically assume every signal becomes an entered trade unless the strategy currently defines it that way.

Lifecycle may need concepts like:

CREATED
WAITING_ENTRY
ACTIVE
CLOSED
EXPIRED
INVALIDATED

Use existing lifecycle conventions wherever possible.

---

# STEP 8 — MARKET OUTCOME TRACKING

Once the ghost trade becomes active, use the canonical Databento-normalized market stream to determine what subsequently happens.

Track at minimum:

## MFE

Maximum favorable excursion.

## MAE

Maximum adverse excursion.

These should be stored both:

* in price/ticks if useful
* normalized to R

Example:

Risk distance = 20 points.

Maximum favorable move = 30 points.

MFE = +1.5R.

Maximum adverse move = 10 points.

MAE = -0.5R.

---

# STEP 9 — DETERMINE EXIT OUTCOME USING ORIGINAL RULES

Ghost trade lifecycle must use the same intended exit semantics that existed at setup time.

Examples include:

* stop loss
* TP1
* TP2
* breakeven move
* trailing logic
* time-based exit
* session close
* strategy-specific management

Do not invent generic exits if a strategy already defines its management rules.

If current strategy-management logic cannot safely be reused without invoking live execution state, isolate the pure trade-management calculation rather than duplicating behavior.

---

# STEP 10 — HANDLE INTRABAR AMBIGUITY HONESTLY

Inspect market-data resolution.

If a bar/tick interval shows both stop and target could have been touched but event ordering cannot be determined, do NOT automatically choose the profitable outcome.

Use:

* event-level ordering when available from Databento
* conservative resolution if exact ordering is unavailable
* or explicit AMBIGUOUS status

Never allow optimistic fill assumptions to create fake expectancy.

Document the chosen rule.

---

# STEP 11 — TRANSACTION COSTS

We need:

GROSS R

and

NET R.

Use existing commission/slippage configuration from the Phase 0 audit where available.

At minimum:

`net_r = gross_r - estimated_cost_r`

Do not claim precision we do not have.

If exact costs cannot be known for ghost trades, mark them clearly as modeled/estimated.

Store enough information to later compare modeled cost against actual live execution.

---

# STEP 12 — THE EDGE LEDGER

Build the smallest reusable profitability ledger.

Its job is NOT to make trading decisions yet.

Its job is simply to answer:

**WHAT HAPPENED?**

For closed ghost observations, calculate grouped statistics.

Required first-level grouping:

**strategy_id × instrument**

Required statistics:

* total observations
* activated trades
* closed trades
* wins
* losses
* breakevens
* win rate
* average gross R
* average net R
* cumulative gross R
* cumulative net R
* average winner R
* average loser R
* profit factor
* max drawdown in R
* average MFE
* average MAE

Do not require session/regime grouping in the first implementation unless the existing architecture makes it trivial.

But the raw observation must preserve enough context for us to segment later.

---

# STEP 13 — EXPECTANCY

The primary performance metric is:

**NET EXPECTANCY IN R PER CLOSED TRADE**

Do not use win rate alone to classify a strategy as profitable.

Example:

55% wins can still be bad.

40% wins can still be excellent.

The system must prioritize expected R after costs.
