TASK: ADD A VOLATILITY INTELLIGENCE MODULE TO THE EXISTING AI TRADING PLATFORM

IMPORTANT: This is an additive context and risk-management feature.

Do not replace, rewrite, or disturb the existing Databento market-data pipeline, strategy engine, Left Brain, Right Brain, trade gateway, TradersPost integration, dashboard routing, journal, learning system, or execution safety controls.

Do not change current strategy entry criteria, edge-score calculations, position-sizing rules, stop-loss calculations, take-profit calculations, or live-trading behavior unless explicitly required below.

The first implementation must be observation-only and feature-flagged.

==================================================
1. OBJECTIVE
==================================================

Add a Volatility Intelligence module that evaluates the broad volatility environment and gives the Left Brain additional market context.

The module must initially evaluate:

1. VIX level
2. VIX intraday direction
3. VIX percentage change
4. VIX short-term rate of change
5. VIX acceleration
6. VIX session percentile
7. Whether VIX data is fresh
8. Whether VIX behavior confirms or conflicts with the current equity-index bias

The initial module must not directly place, block, modify, or close trades.

It must publish context that can later be consumed independently by:

- MNQ
- MES
- MYM
- MGC
- Opening Range Breakout algorithm
- Left Brain
- Right Brain
- Risk-management layer

VIX must never be treated as a simple universal signal such as:

- VIX above 20 means short
- VIX below 15 means long
- Rising VIX automatically blocks longs
- Falling VIX automatically blocks shorts

VIX is context, not a trade signal.

==================================================
2. NON-NEGOTIABLE SAFETY REQUIREMENTS
==================================================

Do not modify the existing Databento ingestion path.

Do not route the primary futures prices through a new provider.

Do not alter the canonical market-price owner for MNQ, MES, MYM, or MGC.

Do not change historical edge scores or current strategy scoring.

Do not alter live execution behavior during this phase.

Do not allow missing VIX data to:

- crash the scanner
- stop the dashboard
- block execution
- change an existing verdict
- default to a bearish or bullish assumption

If VIX data is unavailable, stale, malformed, or unsupported, the module must return an explicit neutral/unavailable state.

All new logic must be protected by feature flags.

Required flags:

VOL_INTELLIGENCE_ENABLED=false
VOL_INTELLIGENCE_OBSERVE_ONLY=true
VOL_INTELLIGENCE_EXECUTION_INFLUENCE=false
VOL_INTELLIGENCE_SCORE_INFLUENCE=false

Default every flag to the safe values above.

The system must remain behaviorally equivalent when VOL_INTELLIGENCE_ENABLED=false.

==================================================
4. VIX DATA SOURCE
==================================================

First determine whether the project’s current Databento subscription and configured datasets provide a reliable VIX index or VIX futures data feed.

Do not assume VIX is present.

If the existing Databento setup supports the required VIX data:

- add the VIX subscription as an independent supplemental stream
- do not modify the existing futures subscriptions
- isolate VIX parsing from the primary instrument pipeline
- reuse existing Databento authentication and connection management where safe

If the existing Databento setup does not provide VIX:

- build a provider adapter interface
- do not hard-code the module to one provider
- implement the adapter so another approved source can be configured later
- keep the module in DATA_UNAVAILABLE status until a supported provider is configured
- do not scrape websites
- do not use delayed data without labeling it delayed
- do not fabricate or approximate VIX from MNQ or MES price action

Create an interface similar to:

VolatilityDataProvider
    get_latest_vix()
    get_vix_history()
    get_provider_status()

The implementation must return normalized timestamps in UTC internally and display Eastern Time on the dashboard.

7. VOLATILITY REGIME CLASSIFICATION
==================================================

Build configurable regime bands.

Do not scatter hard-coded values across the codebase.

Use one centralized configuration structure.

Initial default research bands may be:

CALM:
VIX below 15

NORMAL:
VIX 15 through 20

ELEVATED:
VIX above 20 through 30

EXTREME:
VIX above 30

These are broad contextual bands only.

The module must also evaluate relative behavior because the absolute VIX level alone is insufficient.

Include:

- change from previous close
- change over 1 minute
- change over 5 minutes
- change over 15 minutes
- change over 30 minutes
- session range percentile
- short-term slope
- acceleration
- data freshness

A VIX of 18 rising rapidly may be more important than a VIX of 23 slowly declining.

The output must separately report:

- absolute regime
- current direction
- current rate of change
- acceleration
