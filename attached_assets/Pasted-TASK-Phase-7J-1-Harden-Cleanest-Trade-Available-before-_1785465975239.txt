TASK: Phase 7J.1 — Harden Cleanest Trade Available before final weekly freeze.

CONTEXT

The Cleanest Trade Available feature is now implemented in Main Brain.

Current implementation:

- ports the legacy pickCleanestSetup() ranking algorithm into src/lib/cleanestTrade.ts
- fetches eight /api/status combinations in parallel when the operator clicks the button
- ranks the returned candidates in the browser
- displays the selected candidate in a Main Brain modal

All focused tests and golden suites pass.

GOAL

Prove that the new Main Brain result is identical to the legacy selector and remove avoidable drift, stale-response, and repeated-click risks.

This is a hardening and evidence task.

DO NOT change:

- ranking semantics
- candidate eligibility
- Edge Score
- readiness
- strategy logic
- Databento
- risk calculations
- trade-preview calculations
- execution
- TradersPost
- polling
- authentication
- learning logic
- opposing-structure behavior

PART 1 — PROVE ALGORITHM PARITY

Create shared deterministic fixtures covering:

- READY and POTENTIAL candidates
- higher-edge WAIT versus lower-edge READY
- ties
- missing candidates
- malformed candidates
- Long and Short
- SCALP and SWING
- all supported instruments

Run both:

1. the exact legacy pickCleanestSetup implementation
2. the new src/lib/cleanestTrade.ts implementation

against every fixture.

Assert that both select:

- the same candidate
- the same instrument
- the same mode
- the same direction
- the same readiness
- the same tie winner

Do not merely duplicate expected values in two unrelated tests.

The test must directly compare the two implementations.

PART 2 — CHECK FOR A CANONICAL BACKEND OPTION

Determine whether the existing backend already has enough information to return the cleanest candidate from one atomic snapshot.

Do not build a new ranking system.

Preferred architecture, only if safe:

- one backend endpoint
- one snapshot timestamp
- existing canonical ranking semantics
- one response containing the selected candidate and ranking reasons

If this would require duplicating or changing ranking logic again, do not implement it.

Instead, document why the browser-side compatibility approach remains safer for this weekly checkpoint.

PART 3 — PROTECT AGAINST MIXED-TIME RESPONSES

The eight parallel /api/status responses may complete from slightly different market-state versions.

Add read-only evidence for each response:

- requested instrument
- requested mode
- response timestamp
- market-data timestamp or snapshot identifier, when available
- response age
- request success/failure

Determine whether all candidates came from a sufficiently consistent snapshot.

Do not invent a hard tolerance without checking existing timestamp behavior.

If timestamps are unavailable, expose that fact clearly in diagnostics.

PART 4 — REPEATED-CLICK SAFETY

Prevent overlapping Cleanest Trade scans.

Required behavior:

- while a scan is running, additional clicks do not start another eight-request batch
- the button remains visibly SCANNING
- only the newest valid scan result can update the modal
- an older request batch cannot overwrite a newer result
- all request state clears after success or failure

Use an in-flight guard or request generation identifier.

Do not add a recurring polling loop.

PART 5 — PARTIAL FAILURE BEHAVIOR

Define and test behavior when some status requests fail.

Requirements:

- do not silently treat failed instruments as having no candidate
- show how many combinations succeeded
- show which combinations failed
- label the ranking as PARTIAL when the full candidate universe was not evaluated
- do not claim “cleanest trade available” with full certainty when results are partial

Example:

PARTIAL SCAN
6 of 8 markets evaluated
MGC SCALP and MYM SWING unavailable

If the existing old-home feature had different failure semantics, document and preserve them where practical.

PART 6 — DATA FRESHNESS

The modal must show:

- scan completed time
- selected candidate data time
- age of selected candidate data
- whether the scan was COMPLETE or PARTIAL

If selected data exceeds an existing canonical freshness threshold, show STALE.

Do not create a new trading gate.

This is display-only.

Verify from browser network evidence:

- repeated clicks during the scan do not produce another batch
- opening and closing the modal creates no polling stream
- the normal Main Brain polling interval remains unchanged
