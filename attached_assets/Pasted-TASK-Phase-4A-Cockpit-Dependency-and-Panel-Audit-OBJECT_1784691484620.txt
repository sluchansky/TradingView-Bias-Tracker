TASK: Phase 4A — Cockpit Dependency and Panel Audit

OBJECTIVE

Audit the existing Cockpit dashboard before changing its layout or data bindings.

Do not modify code during this task.

The architecture rule is:

All incoming data feeds the Main Brain.
All operator and diagnostic surfaces read from the Brain Contract or clearly
identified diagnostic extensions owned by the Brain.

AUDIT EVERY COCKPIT PANEL

For every visible Cockpit panel, widget, gauge, badge, table, and status block,
report:

1. Panel/widget name
2. DOM ID or selector
3. Rendering function
4. Current data source paths
5. Whether it currently reads:
   - data.brain
   - canonical top-level /status fields
   - legacy fields
   - duplicated client-side state
   - locally recalculated values
6. Purpose:
   - operator decision
   - supporting diagnostic
   - developer/debug
   - execution monitoring
   - learning/history
7. Whether the panel duplicates information already shown elsewhere
8. Whether it conflicts with the Brain Contract
9. Whether it is per-instrument
10. Whether it can display stale or cross-instrument information
11. Recommended action:
   - retain
   - migrate to brain
   - combine
   - move to developer diagnostics
   - hide by default
   - remove later
12. Recommended canonical source

AUDIT THESE CATEGORIES SPECIFICALLY

- verdict and readiness
- primary edge score and grade
- edge component breakdown
- score adjustments
- confidence governor
- directional confidence
- strict gate diagnostics
- volatility and ATR
- zones and structure
- market intelligence
- thesis state
- historical learning
- auto-research
- execution state
- active trades
- TradersPost state
- prop-account risk state
- feed health and timestamps
- alert diagnostics
- raw webhook data
- journal/review data
- avatar/Main Brain dialogue inputs

IDENTIFY ALL CLIENT-SIDE CALCULATIONS

Find every Cockpit JavaScript calculation that derives or reinterprets:

- score
- verdict
- grade
- direction
- readiness
- risk
- reasons
- confidence
- trade plan
- freshness

Flag each one as:

- safe formatting only
- duplicate calculation
- conflicting calculation
- required diagnostic transformation

PROPOSE THE COCKPIT STRUCTURE

Propose a consolidated Cockpit organized into no more than these primary groups:

1. Brain Decision
2. Market Structure
3. Risk and Execution
4. Diagnostics
5. Learning and History

For each proposed group, list the retained panels and their canonical data paths.

Do not place duplicate primary verdict or score widgets throughout Cockpit.

The Brain Decision section may summarize the decision, but it must use the same
brain.decision and brain.score values as Home.

OUTPUT

Return:

1. Complete current Cockpit widget inventory
2. Current source → recommended source mapping
3. Duplicate/conflicting calculations
4. Cross-instrument or stale-data risks
5. Proposed five-group Cockpit layout
6. Exact migration plan ordered from lowest to highest risk
7. Fields currently missing from the Brain Contract that Cockpit legitimately needs
8. Confirmation that no code was modified

Do not change dashboard JavaScript.
Do not change backend code.
Do not change the Brain Contract.
Do not remove panels.
Do not add Databento.
