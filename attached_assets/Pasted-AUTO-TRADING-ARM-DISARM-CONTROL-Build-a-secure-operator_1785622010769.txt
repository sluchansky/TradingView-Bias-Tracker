AUTO-TRADING ARM / DISARM CONTROL

Build a secure operator-controlled arming system for auto-trading.

This task may add execution-control functionality, but it must not change strategy logic, Databento ingestion, scoring, gates, risk formulas, position sizing, or TradersPost payload calculations.

Keep live execution disabled during development and testing.

Core safety model

Live auto-execution requires both:

1. EXECUTION_MODE=traderspost
2. A valid active operator arm session

If either condition is missing, live orders must be blocked.

Required invariant:

Live-capable mode + DISARMED = no live order

The application must always start DISARMED after:

* Application restart
* Deployment
* Server crash
* Configuration reload
* Arm-session expiration
* Authentication failure
* Safety lockout
* Unknown execution state

Never persist an armed state across restart.

1. Backend arm state

Create a backend-owned arm-state controller.

Do not rely on frontend state or localStorage.

Arm state should include:

* armed: boolean
* armed_at
* expires_at
* armed_by
* arm_session_id
* configured_mode
* effective_mode
* disarm_reason
* last_changed_at
* last_changed_by

The backend is the only source of truth.

Use an in-memory arm state that resets on restart, or a persisted record that is explicitly forced to armed=false during startup.

Recommended default:

* armed=false
* Arm duration: 30 minutes
* Auto-expire at the end of the selected trading window
* Maximum arm duration: 2 hours

2. Separate configured mode from armed state

Expose these states separately:

* Configured mode:
    * disabled
    * paper
    * traderspost
* Effective execution state:
    * disabled
    * paper
    * live_available_disarmed
    * live_armed
    * safety_locked

Examples:

* EXECUTION_MODE=disabled → disabled
* EXECUTION_MODE=paper → paper
* EXECUTION_MODE=traderspost + disarmed → live_available_disarmed
* EXECUTION_MODE=traderspost + armed → live_armed
* Any safety lockout → safety_locked

Do not display LIVE merely because the environment variable is set.

3. Arm endpoint

Create an authenticated state-changing backend endpoint such as:

POST /execution/arm

Required request fields:

* Confirmation phrase
* Requested arm duration
* Instrument allowlist
* Maximum contracts per instrument
* Maximum trades during this arm session
* Maximum session loss
* Optional allowed strategy list

Require an exact confirmation phrase such as:

ARM LIVE AUTO TRADING

Do not accept partial or case-insensitive confirmation.

Before arming, verify:

* Operator is authenticated
* EXECUTION_MODE=traderspost
* Databento is connected and fresh
* No daily loss lockout
* No drawdown lockout
* No unknown broker state
* No unresolved transmission
* No unprotected active position
* No execution reconciliation pending
* TradersPost configuration is present
* Risk profile is valid
* Requested instruments are approved
* Requested contract limits are within hard backend limits

Return a structured response containing:

* Armed status
* Arm-session ID
* Expiration
* Allowed instruments
* Contract limits
* Trade limit
* Session-loss limit
* Effective execution state

Do not expose secrets.

4. Disarm endpoint

Create:

POST /execution/disarm

Disarming must:

* Take effect immediately
* Block new entries
* Cancel or invalidate unclaimed candidates
* Preserve management of existing protected positions unless emergency-stop rules say otherwise
* Record the operator and reason
* Clear the active arm-session ID
* Set effective state to live_available_disarmed or safety_locked

Disarming must not remove an existing protective stop.

Support reasons such as:

* operator_manual
* arm_expired
* deployment_restart
* databento_disconnected
* stale_market_data
* daily_loss_limit
* drawdown_limit
* duplicate_guard_failure
* lre_failure
* broker_state_unknown
* protective_order_failure
* authentication_failure
* system_exception
* emergency_kill_switch

5. Emergency kill switch

Add a prominent backend-controlled kill switch:

POST /execution/kill-switch

The kill switch must:

* Immediately disarm new entries
* Block all new execution attempts
* Mark the system safety_locked
* Require a separate explicit reset before rearming
* Record a critical audit event
* Preserve or safely manage existing protective orders
* Never silently close a live position unless the operator explicitly selects an emergency-close action

Do not combine “stop new entries” and “market close all positions” into one ambiguous button.

Provide separate controls:

* DISARM NEW ENTRIES
* EMERGENCY CLOSE AND LOCK

The emergency-close route must require an additional exact confirmation phrase.

6. Mandatory pre-transmission arm check

Check arm status:

1. At candidate evaluation
2. Before candidate claim
3. Immediately before outbound transmission

The final check must confirm:

* Arm session exists
* Arm session has not expired
* Arm-session ID matches the candidate authorization
* Instrument is allowed
* Strategy is allowed, when restricted
* Contracts are within arm-session limits
* Session trade count is below limit
* Session loss is below limit
* Effective mode is live_armed
* All existing safety gates still pass

Required invariant:

A candidate approved while armed must still be blocked if the system is disarmed before transmission.

7. Arm-session limits

Each arm session must support hard backend limits:

* Allowed instruments
* Maximum contracts per instrument
* Maximum number of trades
* Maximum session loss
* Start time
* Expiration time
* Optional approved strategies
* Optional Long-only, Short-only, or both
* Optional single-position-only setting

Start with conservative defaults:

* One active position maximum
* One contract maximum until changed explicitly
* Maximum 3 trades per arm session
* 30-minute arm duration
* No pyramiding
* No automatic reversal
* Approved instruments only
* Existing prop limits still apply

Arm-session limits may only tighten existing global safety limits, never loosen them.

Display clearly:

* DISARMED
* PAPER
* LIVE AVAILABLE — DISARMED
* LIVE ARMED
* SAFETY LOCKED

Use a large persistent status indicator visible on every Main Brain section.

The panel should display:

* Configured mode

* Armed status
* Arm expiration countdown
* Allowed instruments
* Max contracts
* Trades used / trade limit
* Session P&L / loss limit
* Databento health
* Prop-guard status
* Broker/reconciliation status
* Last disarm reason

Controls:

* ARM AUTO-TRADING
* DISARM NEW ENTRIES
* EMERGENCY KILL SWITCH
* RESET SAFETY LOCK

Require a confirmation modal before arming.

The arm modal must show exactly what is being authorized:

* Instruments

9. Automatic disarm triggers

Automatically disarm when:

* Arm timer expires
* Server restarts
* New deployment starts
* Databento disconnects
* Tick, bar, VWAP, or candidate data becomes stale
* Daily loss limit is reached
* Drawdown limit is reached
* Broker state is unknown
* TradersPost request has ambiguous status
* Protective stop is rejected or missing
* Duplicate-guard integrity fails
* Learning Rule Engine enters a blocking error state
* Authentication session becomes invalid
* Execution-mode configuration changes
* Account or prop profile changes
* Instrument mapping becomes invalid
* An unhandled execution-path exception occurs

Use fail-closed behavior.

10. Existing trade behavior after disarm

Define behavior clearly:

* Disarm blocks new entries immediately.
* Existing protected positions continue normal stop and target management.
* Existing positions must remain visible.
* Protective orders must not be cancelled by ordinary disarm.
* A separate emergency-close command is required to close positions.
* If protective-order state is unknown, lock the system and alert the operator.
* No rearm is allowed until reconciliation completes.

11. Authentication and authorization

All arm, disarm, reset, and kill-switch routes must:

* Require authenticated operator access
* Use POST
* Reject GET
* Enforce backend authorization
* Include CSRF or equivalent protection
* Not be callable anonymously through direct Flask access
* Not rely only on Express authentication if Flask is publicly reachable
* Rate-limit repeated arm attempts
* Record successful and failed attempts

Never put the arm token or control state only in browser storage.

12. Audit records

Record every arm-state change:

* Timestamp
* Operator
* Action
* Previous state
* New state
* Arm-session ID
* Expiration
* Limits
* Confirmation result
* Reason
* Source IP or safe request identifier
* Configured mode
* Effective mode

Every execution attempt must record:

* Whether it was armed
* Arm-session ID
* Time remaining
* Instrument allowed result
* Contract-limit result
* Trade-limit result
* Session-loss result
* Final arm authorization result
* Block reason

Never log passwords, authentication headers, webhook URLs, or secrets.

13. Required tests

Create:

test_auto_trading_arm_control.py

Test at minimum:

Startup and defaults

* Restart always starts disarmed
* Missing mode remains disabled
* Paper mode cannot be armed live
* TradersPost mode starts disarmed
* Published restart clears armed state

Arming

* Correct confirmation arms
* Incorrect confirmation fails
* Unauthenticated request fails
* Expiration is set
* Excessive duration is rejected or clamped
* Invalid instrument is rejected
* Excessive contracts are rejected
* Databento unhealthy blocks arming
* Prop lockout blocks arming
* Unknown broker state blocks arming

Transmission protection

* Disarmed candidate cannot transmit
* Armed candidate can reach mocked live transport
* Disarm before transmission blocks
* Expired arm session blocks
* Wrong instrument blocks
* Contract limit blocks
* Trade limit blocks
* Session-loss limit blocks
* Strategy restriction blocks
* Arm-session ID mismatch blocks

Automatic disarming

* Databento disconnect
* Stale tick
* Stale bar
* Stale VWAP
* Daily loss limit
* Drawdown limit
* LRE blocking failure
* Broker-state unknown
* Protective-stop failure
* Deployment restart
* Unhandled gateway exception

Concurrency

* Two simultaneous arm requests create only one active arm session
* Ten simultaneous identical candidates produce no more than one outbound attempt
* Disarm racing with send blocks or safely resolves deterministically
* Expiration racing with send blocks
* Kill switch racing with send blocks

Existing positions

* Ordinary disarm does not remove stop
* Ordinary disarm does not falsely close trade
* Existing trade management remains active
* Emergency close requires separate confirmation
* Unknown protective-order state prevents rearm

Use mocked outbound transport only.

Zero real TradersPost calls are allowed.
