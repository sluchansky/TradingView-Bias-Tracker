AUTO-TRADING SYSTEM — FULL SAFETY, EXECUTION, AND CONTROL AUDIT

This is an audit-first task.

Do not add new strategies, change scoring formulas, loosen gates, improve signal frequency, redesign the UI, or refactor unrelated code.

The goal is to determine whether the current auto-trading system can safely and correctly move from market data to an executed order.

Do not place a live order during this audit.

Use dry-run, simulation, mocked broker responses, paper mode, or a disabled execution gateway for all execution testing.

Primary audit question

Can the system reliably guarantee that:

1. The correct market data is used
2. The correct strategy and direction are selected
3. All required gates pass
4. Risk and position size are calculated correctly
5. The intended order is created exactly once
6. TradersPost receives the correct payload
7. Duplicate or stale orders are blocked
8. Prop-firm limits cannot be violated
9. Failures default to no trade
10. Every decision and execution attempt is traceable afterward

3. Auto-execution activation audit

Find every switch, environment variable, database flag, UI toggle, command, and fallback that can enable or disable execution.

Report:

Required invariant:

No explicit authorization means no order transmission.

Flag any fail-open behavior as CRITICAL.

4. Data freshness and instrument integrity

Audit the data entering execution decisions.

Verify:

* Databento is the source used by the live decision path
* Instrument mapping is strict for MGC, MNQ, MES, and MYM
* Unknown instruments are rejected
* No unknown ticker silently defaults to MGC or another instrument
* Tick timestamps are checked
* Bar timestamps are checked
* Candidate timestamps are checked
* Thesis timestamps are checked
* VWAP timestamps are checked
* Volatility timestamps are checked
* Stale data blocks execution
* Disconnected or degraded data blocks execution
* Partial bars cannot be mistaken for completed bars where completed bars are required
* CME maintenance periods and market closures cannot generate false actionable signals
* Time-zone handling is consistently Eastern Time or clearly normalized to UTC
* Daylight-saving transitions are handled safely

Create tests for:

* stale tick
* stale bar
* stale VWAP
* stale thesis
* stale candidate
* unknown instrument
* disconnected feed
* empty market state
* maintenance halt
* timestamp in the future
* malformed timestamp

Required invariant:

Missing, stale, conflicting, or invalid market data must produce NO TRADE.

5. Strategy and candidate-selection audit

For each strategy currently eligible for auto-execution, report:

* Strategy key
* Supported instruments
* Supported modes
* Direction rules
* Entry rules
* Stop rules
* Target rules
* Minimum confirmations
* Edge-score requirements
* Whether the strategy is live, paper-only, research-only, or disabled
* Whether the displayed strategy name matches the execution strategy key

Verify:

* Only one final candidate can own an execution cycle
* Candidate ranking is deterministic
* Ties are resolved deterministically
* A lower-ranked candidate cannot overwrite the winner later in the same cycle
* Long and short candidates cannot both become executable
* A stale candidate cannot survive a new market-state cycle
* A candidate cannot execute after its setup is invalidated
* Research and paper-simulation strategies cannot enter the live execution path
* The 16 or more research strategies cannot accidentally bypass the approved live-strategy allowlist
* Strategy aliases cannot cause risk or learning data to be applied to the wrong strategy

Required invariant:

The strategy displayed in the decision trace must be the strategy used to build the order.

6. Direction-integrity audit

Trace every place where Long, Short, Buy, Sell, bullish, bearish, or neutral values are converted.

Verify:

* No stale direction retained from a prior candidate

* Stop and targets are on the correct side of entry
* Long orders require stop below entry
* Short orders require stop above entry
* Targets are directionally correct
* A neutral, conflicted, waiting, or no-trade state cannot reach order creation

Create explicit tests for all supported direction strings and invalid values.

11. Duplicate-order and concurrency audit

Inspect all polling loops, request handlers, workers, timers, and execution functions that can initiate an order.

Verify:

* The same signal cannot execute twice
* Two simultaneous workers cannot execute the same candidate
* A server restart cannot replay the last signal
* A retry after timeout cannot produce a second order
* A delayed TradersPost response cannot cause resubmission
* A frontend request cannot directly execute a trade twice
* Multiple Main Brain polling requests do not trigger execution
* A candidate is atomically claimed before transmission
* The idempotency key is deterministic and persisted
* The duplicate lock survives process restart
* Duplicate detection considers:
    * instrument
    * direction
    * strategy
    * entry
    * signal timestamp
    * execution mode
    * account

Run concurrency tests with at least:

* 2 simultaneous calls
* 10 simultaneous calls
* timeout followed by retry
* server restart after send but before acknowledgement
* duplicate signal received through two paths

Required invariant:

One approved signal may create no more than one broker-side order.

12. Existing-position and order-state audit

* A rejected order cannot appear as an active trade

21. Defect severity classification

Classify findings as:

CRITICAL

A defect can cause:

* Unauthorized live execution
* Duplicate order
* Wrong direction
* Wrong instrument
* Excessive size
* Missing protective stop
* Prop-limit violation
* Execution using stale or invalid data
* Live order from a paper/research strategy
* Fail-open behavior

HIGH

A defect can cause:

* Incorrect target or stop
* Incorrect active-trade state
* Unsafe retry
* Lost reconciliation state
* Journal showing an inaccurate execution outcome

MEDIUM

A defect causes:

* Misleading UI
* Missing diagnostics
* Incomplete audit trail
* Recoverable state inconsistency

LOW

A defect is cosmetic or documentation-only and cannot influence execution.

22. Fixing rules

During the audit:

* Immediately fix CRITICAL defects only when the fix is small, isolated, and clearly testable.
* Do not make broad architectural changes.
* For HIGH, MEDIUM, and LOW defects, document first.
* Do not alter strategy profitability logic.
* Do not loosen any safety restriction.
* Do not change Databento ingestion unless a demonstrated execution-safety defect requires a narrowly scoped fix.
* Every fix must include a regression test.
* After a fix, rerun the relevant audit scenario and safety suite.

24. Live-trading approval standard

Do not declare the system safe for live auto-trading unless all of the following are proven:

* Zero unresolved CRITICAL defects
* Zero unresolved HIGH execution-safety defects
* Strict instrument validation
* Strict direction validation
* Stale-data blocking
* Deterministic candidate ownership
* Correct sizing for all four instruments
* Working prop guards
* Persistent idempotency
* Duplicate concurrency tests pass
* Ambiguous network responses reconcile safely
* Protective stop is guaranteed
* Restart recovery passes
* Execution authorization defaults OFF
* Complete execution audit trail exists
* End-to-end dry runs pass without a live order

Until those standards are met, auto-execution must remain disabled or paper-only.
