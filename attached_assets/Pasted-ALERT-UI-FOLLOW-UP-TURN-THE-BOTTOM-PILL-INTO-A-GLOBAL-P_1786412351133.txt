ALERT UI FOLLOW-UP — TURN THE BOTTOM PILL INTO A GLOBAL PERSISTENT ALERT DOCK

The current App-level READY pill is a good start, but it still does not satisfy the operator goal.

The operator eventually does not want to constantly monitor the engine/dashboard.

The home page must become the central place where important trading alerts appear.

DO NOT change trading logic, scoring, execution, or broker behavior.

This task is UI/alert-routing only.

==================================================
1. DO NOT TRACK ONLY THE SELECTED INSTRUMENT
==================================================

The global alert component must monitor ALL FOUR instruments simultaneously:

MGC
MNQ
MES
MYM

Do not use localStorage selected ticker as the alert eligibility filter.

The selected ticker may affect what opens when an alert is clicked, but it must NOT determine which alerts can appear.

Example:

Operator is viewing MGC.

MNQ becomes READY.

The MNQ alert MUST still appear.

==================================================
2. ALERTS MUST SURVIVE READY → WAIT
==================================================

Do NOT automatically remove an alert just because the underlying setup returns to WAIT.

Once a new actionable alert has fired, preserve it until one of these occurs:

- operator acknowledges/dismisses it
- operator opens the alert and marks it seen
- alert expires according to a clearly defined age policy

Default behavior:

alerts remain until acknowledged.

The live market state changing afterward must not erase the evidence that the alert happened.

==================================================
3. USE AN ALERT QUEUE, NOT ONE SINGLE TOAST
==================================================

Create a small global alert queue.

If multiple instruments alert close together, do not overwrite the previous one.

Example:

09:43 MNQ READY
09:44 MES READY
09:45 MGC ORB QUALIFIED

All three must remain accessible.

Suggested compact display:

[ 🔔 3 ALERTS ] [ latest alert summary ]

Click/tap expands the alert drawer.

Maximum visible compact cards can be limited, but the queue must preserve the recent alerts.

==================================================
4. ALERT TYPES
==================================================

Support at minimum:

LIVE_READY

Meaning:
existing production system reaches READY.

09:30_ORB_SHADOW_QUALIFIED

Meaning:
new four-instrument 09:30 ORB reaches QUALIFIED in SHADOW mode.

09:30_ORB_BREAKOUT_MISSED

Optional informational alert.

POSITION_MANAGEMENT

Existing active-trade warning/management event if already available.

SYSTEM_SAFETY

Examples:
daily cap reached
prop block
Databento stale
execution disabled when operator expects execution

Do not mix low-value diagnostic spam into the operator alert stream.

==================================================
5. CLEARLY DISTINGUISH SHADOW FROM LIVE
==================================================

This is critical.

A shadow ORB alert must NEVER look like a live-order confirmation.

Example:

MNQ
09:30 ORB
SHADOW QUALIFIED
LONG

not:

TRADE ENTERED

unless an actual broker order was transmitted.

Use prominent:

SHADOW

labeling.

10. DEDUPLICATION
==================================================

A READY state persisting for 5 minutes must create ONE alert, not one every poll.

Use a stable identity such as:

strategy
direction

qualified timestamp

Likewise the ORB engine should expose/use its immutable ORB instance/event identity.

A state transition may create a new alert only when it represents a genuinely new event.

==================================================

If an existing server-side alert/event store can safely be reused, prefer it for durable cross-device history.

Do not create a new heavy persistence system if one already exists.
