PART 2 — REPAIR SC3: WAIT MUST NOT ABANDON AN ACTIVE TRADE
----------------------------------------------------

Current defect:

A READY snapshot is captured.

The trade opens.

A later heartbeat returns WAIT.

The current WAIT cleanup calls `_dq_abandon_setup()` and removes the pending
analytics association even though the trade is still active.

When the trade later closes, no matching Decision Quality entry remains.

Repair this behavior.

Before abandoning a pending setup because the verdict is WAIT:

1. Inspect the existing active-trade state for the instrument.
2. Determine whether an active trade corresponds to the pending direction and
   mode.
3. If a matching trade is active, preserve the Decision Quality pending entry.
4. If no matching trade is active, the setup may be abandoned as before.

Do not rely only on instrument presence when the active-trade state includes a
direction.

Use a small diagnostics-only helper if needed, such as:

_dq_has_active_trade(inst, direction, mode)

The helper must:

- Read production trade state only
- Never mutate production trade state
- Fail safely
- Return False on malformed or unavailable state
- Never raise into full_analysis()

Expected sequence:

READY
→ snapshot captured
→ trade opens
→ later WAIT heartbeat
→ snapshot association remains
→ trade closes
→ correct snapshot resolves

Expected untraded sequence:

READY
→ no trade opens
→ later WAIT
→ pending setup is abandoned
→ later READY can be captured fresh

PART 3 — REPAIR SC4: ACTIVE TRADES MUST NOT EXPIRE BY TTL
----------------------------------------------------

Current defect:

`_DQ_SETUP_TTL_MIN = 240` applies equally to:

- untraded READY candidates
- active SCALP trades
- active SWING trades

An active SWING held longer than four hours can lose its analytics association.

Repair the TTL logic so active-trade associations are never removed by the
candidate-expiry process.

During `_dq_expire_old_entries()`:

- Check whether each pending entry corresponds to an active trade.
- If the trade is active, do not expire the entry.
- If the entry is an untraded candidate and exceeds the TTL, expire it normally.

Do not increase the global TTL as the primary fix.

Do not make active SWING trades depend on an arbitrary fixed duration.

Record lifecycle counters separately for:

- expired untraded candidates
- preserved active entries
- resolved entries
- abandoned entries
- unmatched closures

Do not feed these counters into scoring or execution.

PART 4 — REPAIR SC2: REMOVE UNSAFE FIRST-MATCH FALLBACK
----------------------------------------------------

Current defect:

When the expected fingerprint is not found, `_resolve_decision_snapshot()` scans
the pending dictionary and selects the first entry matching the instrument and
possibly the direction.

This can attach an outcome to the wrong snapshot.

Remove the arbitrary first-match behavior.

Required outcome matching behavior:

1. Attempt the exact expected fingerprint or exact known snapshot reference.
2. If an exact match exists, resolve it.
3. If no exact match exists:
   - increment the unmatched-closure diagnostic counter
   - log a sanitized diagnostic message
   - return without updating any snapshot row

Never guess.

Never attach an outcome using:

- instrument only
- first dictionary match
- insertion order
- current global mode when capture-time mode is unknown

A missed analytics outcome is preferable to an incorrectly attributed outcome.

Do not delete or modify unmatched database rows.

PART 5 — CAPTURE-TIME MODE SAFETY
----------------------------------------------------

The audit found that `_resolve_decision_snapshot()` uses:

mt.get("_dq_mode") or TRADING_MODE

but `_dq_mode` is not currently stored on the managed trade.

Do not alter the production meaning of the managed-trade object.

Where safe, attach a namespaced diagnostics-only reference to the managed trade
when the trade is registered, such as:

- `_dq_snapshot_key`
- `_dq_fingerprint`
- `_dq_mode`

Only do this if:

- It does not affect serialization or broker behavior
- It does not alter position management
- It does not change existing API output
- It is ignored by all production logic

Preferred matching order:

1. `_dq_snapshot_key`
2. `_dq_fingerprint`
3. Exact fingerprint reconstructed from immutable capture-time fields
4. Unmatched closure

Do not use the unsafe first-match fallback.

If safely storing the diagnostics reference on the managed trade is not
possible, stop and report rather than guessing.
