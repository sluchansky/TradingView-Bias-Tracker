TASK: Phase 5A — Brain Decision Hierarchy Audit and Contract Design

OBJECTIVE

Define the authoritative decision hierarchy for the trading system.

The current system has a canonical Brain Contract, but the decision process is
still spread across market regime, strategy filters, gates, edge score, verdict,
trade plan, execution, and trade-management logic.

This task must identify the real current order of operations and design one
explicit hierarchy.

DO NOT change live behavior during this phase.

Do not change:

- scoring
- thresholds
- strategy eligibility
- gates
- execution
- sizing
- alerts
- database behavior
- trade management
- dashboard layout
- Brain Contract fields
- Databento
- broker integrations

ARCHITECTURAL GOAL

The eventual authoritative flow should be:

1. Data Integrity
2. Market State
3. Strategy Eligibility
4. Setup Evaluation
5. Decision
6. Risk Approval
7. Execution Plan
8. Active Trade Management

A later phase will implement the hierarchy.

This phase is audit and design only.

==================================================
LEVEL 0 — DATA INTEGRITY
==================================================

Identify all checks that determine whether the system has enough valid and fresh
data to make a decision.

Audit:

- active instrument
- price freshness
- data-feed freshness
- missing indicators
- stale analysis
- cross-instrument contamination guards
- malformed values
- null or object-shaped fields
- session availability
- bar age
- required timeframes
- account/execution-state freshness

Report:

- exact functions
- current ordering
- whether failure blocks analysis, blocks execution, or merely reduces score
- current user-facing verdict or reason
- any conflicting behavior

Proposed hierarchy behavior:

If required data is invalid or stale, no strategy or setup should become READY.

Propose explicit state values such as:

- VALID
- DEGRADED
- STALE
- INVALID

Do not implement them yet.

==================================================

- LONG READY
- SHORT READY
- EARLY READY
- WAIT
- LONG WAIT
- SHORT WAIT

- BLOCKED

For each verdict report:

- exact creation function
- conditions
- precedence
- whether it is strategy-specific

Propose one canonical decision-state enum.

Recommended starting point:

- INVALID_DATA
- NO_STRATEGY
- MONITOR
- SETUP_FORMING
- READY
- BLOCKED_BY_RISK
- ACTIVE_TRADE
- MANAGE
- EXIT

Direction should be a separate field:

- LONG
- SHORT
- null

Do not encode direction inside the state name unless backward compatibility
requires it.

Define exact precedence rules.

Example:

INVALID_DATA outranks everything.
ACTIVE_TRADE outranks new-entry analysis.
BLOCKED_BY_RISK outranks READY.
READY requires an eligible strategy and a valid setup.
SETUP_FORMING means directional intent exists but one or more prerequisites are
missing.
MONITOR means no actionable setup currently exists.

==================================================
PROPOSED CANONICAL HIERARCHY
==================================================

Return a proposed deterministic evaluation sequence.

Example:

Step 0:
Validate instrument and data.

Step 1:
Resolve active-trade state.

Step 2:
Classify market state.

Step 3:
Evaluate and rank strategy eligibility.

Step 4:
Evaluate the highest-priority eligible setup.

Step 5:
Apply hard gates and calculate edge score.

Step 6:
Produce canonical decision state and direction.

Step 7:
Run risk approval.

Step 8:
Create or validate executable trade plan.

Step 9:
Publish Brain Contract.

Step 10:
Allow alerts or execution only when the published state permits them.

Provide exact precedence rules and explain where current behavior differs.
