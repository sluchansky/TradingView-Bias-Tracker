=========================================================
OBJECTIVE
=========================================================

For every visible field in MainBrain.tsx:

1. Identify the exact frontend property path being read.
2. Compare it to the actual live `/main-brain` production payload.
3. Identify the canonical source owner.
4. Classify why the field is empty.
5. Fix valid path mismatches and missing read-only aggregation.
6. Preserve honest empty states where no canonical value exists.

The finished dashboard must populate every field for which canonical source data
already exists.

It must not fabricate values merely to fill the mockup.

=========================================================
STAGE 4 — CHECK FRONTEND PATHS FIRST
=========================================================

Before changing backend code, compare MainBrain.tsx paths directly against the
real payload.

Look specifically for:

- snake_case vs camelCase
- nested object vs top-level field
- list vs dictionary
- string vs numeric value
- different field names
- different availability structure
- arrays nested under items, records, trades, or strategies
- timestamps nested under metadata
- instrument-specific maps
- section wrappers such as data, summary, state, current, or status
- backend null values rejected by overly strict frontend guards

Fix frontend mappings when the backend already exposes the canonical value.

Prefer centralized adapter functions rather than scattered fallback chains.

Example structure:

normalizeMainBrainPayload(rawPayload)

The normalizer may:

- map known canonical paths
- normalize valid types
- preserve null/unavailable states
- handle documented schema versions

It must not calculate new trading values or invent defaults.

=========================================================
STAGE 5 — CHECK BACKEND AGGREGATION SECOND
=========================================================

Only after frontend path mismatches are exhausted, inspect the Phase 7B builder.

For each missing field, determine whether a canonical read-only source already
exists elsewhere in the codebase.

If it does:

- expose it through the correct `/main-brain` section
- preserve canonical ownership
- fault-isolate the field or section
- do not mutate any source
- do not call execution or trading functions with side effects
- do not duplicate calculations
- do not reimplement business logic

Examples of potentially valid additive aggregation:

- already-computed verdict confidence
- already-computed market driver
- existing volatility diagnostics
- existing active-trade management state
- existing broker readiness flag
- existing duplicate guard state
- existing closed-trade summary
- existing Coach performance summary
- existing strategy scanner failed conditions

Every additive field must document:

source function → source path → output path → type → failure fallback

=========================================================
STAGE 6 — HONESTLY CLASSIFY GENUINELY MISSING DATA
=========================================================

Some fields may not yet exist canonically.

Examples already known as deferred:

- execution last_outcome
- complete decision-event history
- per-strategy historical statistics

Do not fabricate these.

For every genuinely missing field:

- retain an explicit unavailable label
- explain why it is unavailable
- avoid a large blank area
- use compact presentation
- identify the future owning subsystem

Examples:

“Last outcome not captured yet.”

“No active trade.”

“No actionable trade plan.”

“No closed trades in the selected period.”

“Strategy history not yet available.”

“Partial timeline.”

The UI should distinguish an expected empty state from a broken section.
