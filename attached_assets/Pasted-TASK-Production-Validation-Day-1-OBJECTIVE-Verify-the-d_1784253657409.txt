TASK: Production Validation — Day 1

OBJECTIVE

Verify the deployed Phase 1–3 system under real incoming market alerts.

This is testing only.

Do not add features.
Do not modify strategy logic.
Do not tune thresholds.
Do not enable thesis enforcement.
Do not change risk, contracts, entry, stop, targets, scoring, or TradersPost behavior.

Keep:

THESIS_ENFORCEMENT_MODE=shadow

--------------------------------------------------
1. VERIFY THE LIVE DEPLOYMENT
--------------------------------------------------

Confirm:

- The production application is running.
- The production dashboard loads.
- The correct production database is connected.
- TradingView webhooks are reaching production.
- Discord notifications are reaching the correct channel.
- The Market Thesis panel updates.
- The Shadow Validation panel updates.
- TradersPost configuration remains unchanged.
- No development or localhost endpoint is being used.

Report the active production URL and current Git commit.

Do not expose secrets.

--------------------------------------------------
2. WATCH REAL ALERT PROCESSING
--------------------------------------------------

Observe at least one complete alert sequence for an enabled instrument.

Verify the sequence:

1. TradingView alert received
2. Instrument identified correctly
3. Alert stored or processed once
4. Thesis updated once
5. Thesis status updated correctly
6. Confidence updated correctly
7. Evidence For and Evidence Against updated
8. Dashboard reflects the change
9. Discord sends only the intended notification
10. Shadow thesis gate records an evaluation when READY occurs

There must be no:

- Duplicate webhook processing
- Duplicate thesis transitions
- Duplicate Discord messages
- Duplicate journal entries
- Duplicate TradersPost submissions

--------------------------------------------------
3. VERIFY SHADOW MODE

For every READY setup, confirm the system records:

- Original verdict
- Thesis alignment
- WOULD_ALLOW or WOULD_BLOCK
- Confidence adjustment
- Reasons
- Thesis ID
- Instrument
- Timestamp

The shadow result must not alter:

- READY or WAIT verdict
- Entry
- Stop
- Targets
- Contracts
- Risk
- Auto-trade state
- TradersPost payload

Add a clear test assertion or production log proof that the original verdict remains unchanged after shadow evaluation.

--------------------------------------------------
4. VERIFY THESIS STATE TRANSITIONS
--------------------------------------------------

Confirm the dashboard safely handles all observed states:

- NEUTRAL
- FORMING_LONG
- FORMING_SHORT
- READY_LONG
- READY_SHORT
- INVALIDATED
- COOLDOWN

Do not artificially place a trade to create a state.

Safe test payloads may be used only when they cannot reach TradersPost.

For each transition, confirm:

- Previous state
- New state
- Previous confidence
- New confidence
- Reason
- Thesis ID
- Event timestamp

--------------------------------------------------
5. VERIFY RESTART RECOVERY
--------------------------------------------------

Perform one controlled application restart during a non-trading period.

Before restarting, record the active thesis state.

After restarting, verify:

- The application starts normally.
- Database connection restores.
- Recent safe thesis data can be restored.
- Stale thesis data is rejected.
- Restored READY state cannot submit an order.
- No Discord transition is resent merely because of restart.
- No duplicate history event is created.
- The dashboard reconnects automatically.

Do not restart while an order or live position is being managed.

--------------------------------------------------
6. VERIFY OUTCOME TRACKING
--------------------------------------------------

For any setup that naturally triggers and completes, confirm the outcome record includes:

- Instrument
- Direction
- Entry timestamp
- Thesis ID
- Confidence at entry
- Alignment
- Shadow decision
- Entry
- Stop
- Targets
- Entry triggered status
- Final outcome
- Final R
- Target-first or stop-first result

Do not classify an untriggered setup as a winner or loser.

Confirm the outcome links back to the correct shadow evaluation.

--------------------------------------------------
7. CHECK PRODUCTION LOGS
--------------------------------------------------

Review production logs for:

- Exceptions
- Database write failures
- Discord failures
- Invalid webhook payloads
- Unknown instruments
- Missing thesis fields
- Duplicate processing
- Timeout errors
- Restart recovery errors
- TradersPost errors
- Frontend API errors

Separate harmless warnings from real failures.

Do not hide or suppress errors merely to make the logs appear clean.

--------------------------------------------------
8. CREATE A VALIDATION REPORT
--------------------------------------------------

Provide a concise report with:

DEPLOYMENT

- Production URL
- Commit hash
- Branch
- Deployment status
- Current enforcement mode

ALERT PROCESSING

- Alerts received
- Alerts successfully processed
- Duplicate alerts
- Unknown or rejected alerts

THESIS

- Thesis transitions
- READY events
- Invalidations
- Restored theses
- Stale theses rejected

SHADOW GATE

- Evaluations
- WOULD_ALLOW
- WOULD_BLOCK
- Missing evaluations
- Confirmed live behavior changes: must equal zero

INTEGRATIONS

- Dashboard status
- Discord status
- Database status
- TradersPost status

ERRORS

- Exceptions
- Failed writes
- Duplicate events
- Missing data
- Unresolved issues

--------------------------------------------------
9. CHANGE CONTROL
--------------------------------------------------

During validation, make changes only for confirmed bugs involving:

- Deployment failure
- Broken production API
- Missing database writes
- Duplicate processing
- Incorrect instrument mapping
- Dashboard crashes
- Discord duplication
- Restart safety
- TradersPost safety

Before fixing a bug:

1. Document the observed behavior.
2. Identify the root cause.
3. Add a regression test.
4. Make the smallest possible correction.
5. Run all affected tests.
6. Confirm no trading logic changed.

Do not perform cleanup, redesign, optimization, or unrelated refactoring.

--------------------------------------------------
DEFINITION OF DONE
--------------------------------------------------

Production Validation — Day 1 is complete when:

1. The deployed app remains healthy.
2. At least one real alert sequence is verified end to end.
3. Thesis updates exactly once per event.
4. Shadow evaluations are recorded correctly.
5. Shadow mode causes zero live behavior changes.
6. Dashboard and Discord display the correct information.
7. Restart recovery is proven safe.
8. No duplicate order or message path is detected.
9. Any legitimate bug has a regression test.
10. A validation report is provided.

Do not begin another development phase after completion.

Stop and return the validation report for review.
