TASK: Phase 5F.1 — Decision Snapshot Lifecycle Repair

CRITICAL CONTEXT

Phase 5F validation identified two diagnostics-only lifecycle defects:

1. A READY setup can be captured, return to WAIT, and later become READY again
   with the same instrument and direction.

   Because `_DQ_PENDING_BY_INST` still contains the original key, the later
   READY setup is incorrectly treated as a repeated heartbeat and is not
   captured.

2. `_DQ_PENDING_BY_INST` currently has only one slot per instrument.

   A direction change can overwrite the prior pending snapshot key, leaving the
   earlier database row unresolved.

These defects do not affect production trading, scoring, verdicts, or execution,
but they can make Decision Quality analytics incomplete or inaccurate.

- Gate thresholds

- Auto-trade eligibility

PART 2 — DEFINE SNAPSHOT IDENTITY
----------------------------------------------------

Do not use only:

instrument + direction

as the identity of a Decision Quality setup.

Create a diagnostics-only setup identity using stable values already available
at the READY capture point.

Prefer, in order:

1. Existing trade ID or setup ID
2. Existing candidate ID
3. Existing alert/event identity
4. A deterministic diagnostics-only fingerprint

A fallback fingerprint may include:

- instrument
- direction
- mode
- strategy key
- entry price
- stop price
- target values
- setup/event timestamp

Do not add this identity to production scoring objects if a parallel
diagnostics value is safer.

Do not use the current wall-clock timestamp alone to determine whether two READY
events are the same setup.

----------------------------------------------------
PART 3 — REPLACE THE SINGLE INSTRUMENT SLOT
----------------------------------------------------

Replace the one-key-per-instrument assumption with a diagnostics-only structure
that can distinguish simultaneous or sequential setups safely.

Acceptable patterns include:

DQ_PENDING_BY_SETUP_ID = {
    setup_id: snapshot_key
}

or:

DQ_PENDING_BY_INST = {
    "MNQ": {
        setup_id: snapshot_key
    }
}

The structure must support:

- Long and Short independently
- SCALP and SWING independently
- Sequential setups with the same instrument and direction
- More than one unresolved analytics snapshot without overwriting an older key

Bound memory usage and remove completed or abandoned entries.

Do not change production trade state.

----------------------------------------------------
PART 4 — READY HEARTBEAT DEDUPLICATION
----------------------------------------------------

Repeated evaluation of the exact same READY setup must still be captured once.

Test this sequence:

READY setup A
READY setup A heartbeat
READY setup A heartbeat

Expected:

- One database snapshot
- One pending diagnostics entry

Test this separate sequence:

READY setup A
WAIT / invalidated
READY setup B with the same instrument and direction

Expected:

- Setup B receives a new snapshot
- Setup A does not block Setup B

The distinction must be based on setup identity, not merely instrument and
direction.

----------------------------------------------------
PART 5 — LIFECYCLE CLEARING
----------------------------------------------------

Audit and safely clear diagnostics entries when a setup is no longer pending.

At minimum account for:

- Trade resolved as Win
- Trade resolved as Loss
- Breakeven
- Manual trade closure
- Setup invalidation
- READY reverting to WAIT
- Candidate cancellation
- Auto-trade cancellation
- Direction flip
- Mode change
- Failed snapshot insert
- Failed outcome update
- Application restart

Do not hook into a lifecycle event if doing so would change production behavior.

Diagnostics cleanup must be fail-open:

- A diagnostics exception must never block trading
- A database failure must never block trading
- Cleanup failure must only log diagnostics

If no safe lifecycle hook exists for a condition, use bounded expiry and report
that limitation explicitly.

----------------------------------------------------
PART 6 — OUTCOME MATCHING
----------------------------------------------------

Resolve outcomes using the strongest available identity.

Prefer:

- trade ID
- snapshot ID stored with the trade diagnostics
- setup ID
- exact snapshot key

Do not resolve an outcome using only the latest pending entry for an instrument
when more than one pending setup may exist.

Prove that:

- An old unresolved Long snapshot cannot receive a newer Long trade’s outcome
- A Long snapshot cannot receive a Short trade’s outcome
- A SCALP snapshot cannot receive a SWING trade’s outcome
- Two sequential trades on one instrument resolve independently
- Duplicate closure notifications remain idempotent
- Closure without a matching snapshot is a safe no-op

Do not alter the production trade object unless adding a namespaced
diagnostics-only reference is demonstrably safe.

PART 7 — DATABASE ORPHAN HANDLING
----------------------------------------------------

Do not delete historical snapshots silently.

Add a diagnostics status only if needed, such as:

- pending
- resolved
- abandoned
- expired

Do not classify an unresolved row as a losing trade.

Analytics reports must exclude:

- pending snapshots
- abandoned snapshots
- expired snapshots

They may be reported separately as capture-quality diagnostics.

Return counts for:

- captured
- pending
- resolved
- abandoned
- expired
- unmatched closures

Do not rewrite old rows unless explicitly required and covered by tests.

PART 8 — DQ_DB_READY FAILURE PATH
----------------------------------------------------

Fix the lifecycle behavior where `_resolve_decision_snapshot()` returns before
clearing its in-memory diagnostics entry when `DQ_DB_READY` is false.

The expected behavior is:

- Trading remains unaffected
- The in-memory entry does not permanently block future analytics captures
- Database unavailability is logged diagnostically
- No exception escapes into the trade closure path

Do not fabricate a resolved database outcome when the database is unavailable.
