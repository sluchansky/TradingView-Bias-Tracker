PHASE 7D — LEFT NAVIGATION ROUTE AUDIT AND PAGE ACTIVATION

OBJECTIVE

Audit every item in the Main Brain left navigation and make each visible navigation item behave honestly.

The current production dashboard shows several left-side items that appear inactive or unreachable, including Coach.

The goal is to determine, for each item, whether:

1. A real page already exists but is not wired correctly
2. A route exists but the navigation button points to the wrong path
3. A page exists only as an embedded Main Brain panel
4. The item is a placeholder with no implemented page
5. The item should be temporarily disabled or hidden

Do not build large new feature pages until the audit is complete.

NON-NEGOTIABLE CONSTRAINTS

- DO NOT modify Databento ingestion
- DO NOT modify strategy logic
- DO NOT modify Edge Score calculations
- DO NOT modify learning calculations
- DO NOT modify TradersPost or execution behavior
- DO NOT modify active trade management
- DO NOT change API payload contracts unless required to expose an already-existing page
- DO NOT create fake data to populate unfinished pages
- DO NOT make an inactive navigation item look functional unless it truly works
- Preserve the current Main Brain dashboard exactly unless a small navigation fix is required

VISIBLE NAVIGATION ITEMS TO AUDIT

Audit every left-side item currently rendered, including at minimum:

- Main Brain
- Analysis
- Scanner
- Active Trades
- Journal
- Coach
- Alerts

Also inspect any additional visible or conditionally rendered navigation items.

TASK 1 — BASELINE AND INVENTORY

Before editing:

1. Record branch and HEAD
2. Record working-tree status
3. Run the current Main Brain frontend tests
4. Run TypeScript type checking
5. Run the production build
6. Record the exact current navigation labels, icons, click handlers, route targets, and disabled states

Create an inventory table:

| Nav item | Current target | Route exists | Page component exists | API exists | Current behavior | Recommended action |

Do not modify code until this inventory is complete.

TASK 2 — TRACE THE ROUTING ARCHITECTURE

Read and document:

- MainBrain.tsx
- the left-navigation component
- React router configuration
- Express route handling
- Flask routes related to these pages
- any static HTML legacy dashboards
- any iframe or external-page navigation behavior
- any auth or proxy behavior that affects route access

Determine whether the application uses:

- React Router
- location.href navigation
- window.open
- anchors
- state-based tabs
- server-rendered routes
- a mixture of these

Avoid introducing a second routing pattern unless absolutely necessary.

TASK 3 — CLASSIFY EVERY NAV ITEM

Assign each item exactly one classification:

A. FULL PAGE EXISTS
A functioning page and route already exist.

B. COMPONENT EXISTS, ROUTE MISSING
A usable component exists but is not reachable directly.

C. EMBEDDED PANEL ONLY
The feature exists only inside Main Brain and has no dedicated page.

D. LEGACY PAGE EXISTS
An older page exists outside the new operator console.

E. PLACEHOLDER ONLY
The item has no real implementation.

F. INTENTIONALLY DISABLED
The item is deliberately unavailable because its phase is not complete.

Include evidence for each classification with file paths and route names.

TASK 4 — APPLY THE SMALLEST HONEST FIX

For items classified A or B:

- Wire the navigation item to the existing real page
- Reuse the existing routing architecture
- Preserve authentication
- Preserve browser back/forward behavior
- Preserve direct URL access when supported
- Ensure refreshing the page does not break the route

For items classified C:

Choose one of these based on the existing architecture:

1. Navigate to Main Brain and scroll/focus the corresponding panel, or
2. Add a lightweight dedicated view that reuses the existing panel component

Do not duplicate business logic.

For items classified D:

- Do not automatically link to the legacy page
- Determine whether it is safe and appropriate
- Clearly label it as legacy if it must remain accessible
- Prefer the current operator-console implementation

For items classified E or F:

- Disable the item visibly
- Add a small “Coming Soon” or “Not yet available” indicator
- Prevent click behavior
- Do not leave it looking active
- Do not fabricate a page

TASK 5 — COACH PAGE DECISION

Give Coach special attention.

Audit whether the system already has:

- CoachPanel
- learning status
- LRE eligibility
- weight_updated
- thesis_resolved
- last_resolved
- learning influence
- sample count
- strategy weights
- performance summaries
- learning audit history

If a complete Coach page already exists:
- Wire it correctly

If only CoachPanel exists:
- Create a lightweight dedicated Coach route by reusing the existing CoachPanel and already-available learning data
- Do not add new learning calculations
- Do not invent recommendations
- Do not create fake strategy performance

The dedicated Coach page may contain only existing truthful data:

COACH STATUS
- Learning enabled
- LRE eligible
- Weight updated
- Thesis resolved
- Last resolved time
- Learning influence

LEARNING DATA
- Available sample count
- Existing strategy weights
- Existing performance values
- Existing recent learning events

If data is unavailable, show UNKNOWN or “No data available.”
