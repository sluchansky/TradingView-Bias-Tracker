TASK: Stop Production Data Loss After Republish

OBJECTIVE

Find and correct why current dashboard and bot state disappears after every production republish.

This is a persistence and recovery task only.

Do not change trading logic.
Do not change thresholds.
Do not change scoring.
Do not change risk.
Do not enable thesis enforcement.
Do not change auto-trading behavior.
Keep:

THESIS_ENFORCEMENT_MODE=shadow

==================================================
PROBLEM
==================================================

After every production republish, current dashboard and bot data is wiped or reset.

Determine exactly which state is currently stored only in:

- Python globals
- in-memory dictionaries
- process-local caches
- JSON files
- CSV files
- SQLite files
- temporary files
- deployment filesystem
- browser localStorage only

A production republish creates a new process and must not be expected to preserve process memory or deployment filesystem data.

==================================================
4. DEFINE PERSISTENT VERSUS TEMPORARY STATE
==================================================

Classify each state into one of these groups:

A. MUST PERSIST

Examples:

- thesis records
- shadow evaluations
- journal entries
- completed outcomes
- open managed positions
- manual trades
- strategy performance
- learning records
- duplicate-prevention records needed across restart
- submitted TradersPost request identifiers

B. MAY RESTORE IF FRESH

Examples:

- current thesis snapshot
- current market bias
- setup-forming state
- latest analysis
- current confidence
- Fast Entry context

These must have timestamps and expiration rules.

C. MUST NOT RESTORE AS ACTIONABLE

Examples:

- READY-to-submit state
- pending auto-entry command
- stale order-management action
- unsent TradersPost payload
- old fast-entry trigger
- old one-minute candle trigger
- old countdown state

These may be restored for display or audit only, but never as executable state.

D. UI PREFERENCES ONLY

Examples:

- selected dashboard section
- selected AI Decision Center tab
- collapsed panels
- instrument display preference

These may remain in browser localStorage unless server-wide persistence is intended.

==================================================
5. IMPLEMENT THE SMALLEST SAFE FIX
==================================================

After proving the root cause, make the smallest persistence correction.

Requirements:

1. Persist required server state in the existing production SQL database.

2. Do not use:
   - local JSON as production persistence
   - CSV as production persistence
   - deployment filesystem
   - process memory as the only copy
   - SQLite inside the deployment

3. Add timestamps to restorable state.

4. Add state versioning where needed.

5. Use atomic database transactions for linked records.

6. Restore only fresh, eligible state.

7. Stale state must be rejected and logged.

8. Restored READY state must be downgraded to non-actionable display state.

9. A restored record must never:
   - submit a TradersPost request
   - create a broker order
   - send a duplicate Discord transition
   - create a duplicate journal entry
   - create a duplicate thesis transition
   - create a duplicate shadow evaluation

10. Preserve all current calculations and decisions.

==================================================
6. SAFE BOOT RECOVERY RULES
==================================================

At production startup:

1. Connect to the production database.

2. Load persistent records.

3. Restore eligible current state only if:

   - instrument matches
   - schema version matches
   - timestamp is within the approved freshness window
   - state is not already completed
   - state is not invalidated
   - no newer state exists

4. Mark restored state explicitly:

   restored_from_persistence=true

5. Restored READY state must become:

   RESTORED_REVIEW_REQUIRED

or the closest existing non-actionable equivalent.

Do not introduce a new trading verdict if one already exists for this purpose.

6. Restored state cannot call:

- TradersPost
- broker execution
- Discord transition delivery
- journal creation
- thesis transition creation
- shadow evaluation creation

7. Only new post-restart market evidence may create a new actionable READY event.

- zero duplicate TradersPost submissions

8. DO NOT PRESERVE STALE MARKET DATA FOREVER
==================================================

- thesis snapshot
- setup-forming state
- Fast Entry state

- READY state

Use existing session and timeframe rules where available.

Do not invent arbitrary windows if existing expiry logic already exists.
